# My observation is that queries are like the legal issue, keys are the short case descriptions, and values are the rulings and reasoning. Softmax turns the match scores into weights, one per key, that are all positive and add up to 1. The output is then the weighted sum of all the values. Attention doesn't pick the single best match. It blends every value in proportion to how well each key matched the query. One thing that held up in this analogy is that the key decides how much weight each ruling gets, but the value carries the ruling and reasoning, just like a researcher who reads the short case descriptions first and only then reads the full rulings. What broke was authority. Two cases that matched the question equally well got the same weights, even if one was binding and the other wasn't, because the weights depend only on how well the keys match the query. That led me to the idea of adding a bonus for authoritative cases to the scores before softmax. How big the bonus should be is an open design choice. If it's very large, the other cases effectively disappear. If the bonus is small, authority still breaks ties, but the other cases still contribute. I haven't tested either size. Softmax is the step that turns scores into slices of a pie that add up to 1, so if the adjustment comes after softmax, the weights would no longer add up to 1. Adding the bonus before softmax is in the same family as my causal masking, but I haven't tested whether it would actually help in practice.

# KV cache analogy: It’s like writing detailed notes the first time you read a textbook chapter, so for every exam question after that you just glance at your notebook instead of rereading the whole chapter. Reading the chapter and writing detailed notes is the expensive, one time cost, same as computing K and V for a token the first time. Glancing at the notebook for each new exam question instead of rereading the chapter is the reuse, same as pulling the already computed K and V back out of the cache instead of recomputing them.

# Where it broke: the notebook picture predicts cost increases linearly, so doubling the cache should double the cost. Our actual benchmark showed about 0.001014 seconds per token at 100 tokens and about 0.001165 seconds per token at 200, only about a 15 percent increase, nowhere close to doubling. We split per token cost into two parts: variable cost, comparing the new token against everything already in the cache, which does grow as the cache gets longer, and fixed cost, the feedforward network and projections run on just the single new token, which stays the same no matter how long the cache gets. Working the numbers out, variable cost was about 0.000151 and fixed cost was about 0.000863, out of a total of 0.001014, so fixed cost was more than five times bigger than variable cost. That’s why doubling the cache only moved the total by 15 percent instead of 100. At larger scale, where the cache grows much longer, the balance flips and the variable cost eventually dominates, matching the original linear prediction.
